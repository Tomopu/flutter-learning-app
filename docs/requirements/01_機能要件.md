# 機能要件

## 1. 目的

本ドキュメントは、Flutter学習アプリのMVPで実現する機能要件を定義する。

MVPでは、教材閲覧、コード編集、サーバー側ビルド、実行結果プレビュー、ログ確認、LLM質問を1つの学習体験として成立させることを目的とする。

また、MVPの段階から管理者向け画面を用意し、教材を手動で追加・編集できること、LLMを使って教材とロードマップの下書きを作成できることを目的に含める。

特に、Flutterコードの実行方式は、テンプレート差し替え方式ではなく、MVPの段階からサーバービルド方式を採用する。

## 2. MVPの基本方針

MVPでは、最初の対象をFlutterに限定する。ただし、将来的に他の言語やフレームワークへ拡張できるよう、機能概念はFlutter専用にしすぎない。

MVPで検証する中心価値は、次の通りである。

- 教材を読みながらコードを書ける
- 書いたFlutterコードをWebアプリ上から実行できる
- ビルド結果、プレビュー、エラー内容を同じ画面で確認できる
- 教材内容、現在のコード、ログを踏まえてLLMに質問できる
- 管理者がWeb画面から教材を追加・編集できる
- 管理者がLLMを使ってロードマップと教材の下書きを生成できる
- コードをブラウザ上に保存できる
- プロジェクト全体をローカルへダウンロードし、ローカルからアップロードできる
- 破壊的な変更をした場合に、ファイル単位またはプロジェクト単位で初期状態へ戻せる

## 3. MVPの実装フェーズ

MVPは、次の2段階に分けて実装する。

### 3.1 第一段階: ローカルDockerアプリケーション方式

第一段階では、フロントエンド、バックエンド、データベース、ビルド実行環境をすべてユーザーのローカルマシン上のDockerで動作させる。

サーバービルドも、ユーザーのローカル環境に作成したDockerコンテナ上で実行する。この段階では、外部公開や複数ユーザー利用よりも、教材閲覧、コード編集、ビルド、プレビュー、LLM連携、教材管理の一連の体験をローカルで安定して動かすことを優先する。

### 3.2 第二段階: クラウドサーバービルド方式

第二段階では、GCP、AWSなどのクラウド環境にアプリケーションをデプロイする。

ビルド要求ごとに、クラウド上で一時的なワークスペースまたはコンテナを生成し、その中でFlutter Webビルドを実行する。ビルド完了後は成果物をプレビュー用に配置し、不要なワークスペースは破棄する。

第二段階では、認証、権限管理、ビルドキュー、リソース制限、成果物ストレージ、監視、コスト管理を追加で検討する。

## 4. ユーザー種別

### 4.1 学習者

MVPでは、学習者は開発者本人または限られた利用者を想定する。

学習者は、教材を選択し、教材本文を読み、コードを編集し、サーバー側でFlutter Webビルドを実行し、結果を確認する。

### 4.2 管理者

MVPでは、管理者向け画面を実装対象に含める。

管理者は、教材を手動で追加・編集し、LLMによってロードマップと教材の下書きを生成し、公開状態を管理できる。

初期段階では開発者本人が管理者を兼ねる。ログインや権限管理を本格実装しない場合でも、学習者向け画面と管理者向け画面は画面上の責務として分離する。

## 5. 教材管理

### 5.1 教材一覧表示

システムは、登録済みの教材一覧を表示できる。

教材一覧では、少なくとも次の情報を表示する。

- 教材タイトル
- 概要
- 対象レベル
- 対象技術
- プログラミング言語ラベル
- 公開状態

MVPでは、教材データはMarkdownおよびメタデータファイル、またはアプリケーション内の教材データストアで管理する。

### 5.2 教材詳細表示

システムは、選択した教材の詳細を表示できる。

教材詳細では、少なくとも次の情報を表示する。

- 教材本文
- 学習目標
- 初期プロジェクト
- 実行またはビルドの結果
- LLM質問欄

### 5.3 Markdown表示

システムは、Markdown形式で記述された教材本文を画面に表示できる。

Markdownでは、見出し、本文、コードブロック、リスト、リンクを扱えることを必須とする。

### 5.4 教材追加

管理者は、管理者向け画面から教材を追加できる。

MVPでは、少なくとも次の項目を入力できるようにする。

- 教材タイトル
- 概要
- 対象レベル
- 対象技術
- プログラミング言語ラベル
- 学習目標
- 教材本文
- 初期プロジェクト
- 模範解答または参考プロジェクト
- 公開状態

### 5.5 教材編集

管理者は、既存教材を管理者向け画面から編集できる。

MVPでは、教材本文、メタデータ、初期プロジェクト、模範解答または参考プロジェクト、公開状態を編集対象とする。

教材を編集した場合は、学習者向け画面に反映される。ただし、公開中教材を直接上書きするか、draftとして保存してから公開するかは、実装時のデータ管理方式に合わせて決定する。

### 5.6 プログラミング言語ラベル

管理者は、各教材にプログラミング言語名またはフレームワーク名のラベルを付与できる。

MVPでは、少なくとも次のようなラベルを扱えるようにする。

- Flutter
- Dart
- JavaScript
- TypeScript
- React
- Next.js
- Python
- Go

ラベルは複数付与できることを想定する。たとえば、Flutter教材には`Flutter`と`Dart`を付与できる。

学習者向け教材一覧および管理者向け教材一覧では、プログラミング言語ラベルで教材を絞り込み、並び替えできる。

### 5.7 教材公開状態管理

システムは、教材の公開状態を管理できる。

MVPでは、少なくとも次の状態を扱う。

- `draft`: 下書き
- `published`: 公開中

MVPでは`review`状態は実装しない。

教材の状態は`draft`と`published`の2種類に限定する。複数人で教材レビューを行う段階になった場合に、将来拡張として`review`状態を追加する。

### 5.8 教材一括操作

管理者は、管理者向け教材一覧で複数の教材を選択し、一括操作を実行できる。

MVPでは、少なくとも次の一括操作を扱う。

- 選択した教材を`published`にする
- 選択した教材を`draft`にする
- 選択した教材を削除する

削除は破壊的な操作であるため、実行前に確認を表示する。将来的には、物理削除ではなくアーカイブや論理削除を検討する。

### 5.9 LLMロードマップ・教材生成

管理者は、管理者向け画面からLLMを使ってロードマップと教材の下書きを生成できる。

LLM教材生成では、個別教材を独立して直接生成するのではなく、到達目標と成果物を先に定義し、その成果物へ到達するまでのロードマップを細かいステップに分割したうえで、各ステップに対応する教材を生成する。

このフローにより、教材同士の重複や抜け漏れを減らし、学習者が段階的に成果物へ近づける構成にする。

LLM教材生成では、少なくとも次の入力を扱う。

- 到達目標
- 最終的に作る成果物
- 対象レベル
- 前提知識
- 扱いたいWidget、API、設計トピック
- ロードマップの粒度
- 各ステップで作る中間成果物の方針
- 想定する初期プロジェクトの方針
- 期待する完成プロジェクトの方針

LLM教材生成では、少なくとも次の出力を扱う。

- 全体ロードマップ
- ステップ一覧
- 各ステップの教材タイトル
- 各ステップの学習目標
- 各ステップの教材本文
- 各ステップの初期プロジェクト
- 各ステップの完成プロジェクトまたは参考プロジェクト
- 各ステップの確認観点

LLMが生成したロードマップと教材は、そのまま公開せず、必ず`draft`として保存する。

### 5.10 LLM教材修正

管理者は、既存教材に対してLLMによる修正案を生成できる。

MVPでは、修正案の自動反映は必須としない。管理者が生成結果を確認し、必要に応じて手動で教材本文やコードへ反映する。

## 6. コード編集

### 6.1 コードエディタ表示

システムは、ブラウザ上でコードを編集できるエディタを表示する。

MVPでは、Monaco Editorの利用を候補とする。

### 6.2 編集対象ファイル

MVPでは、編集対象ファイルを限定しない。

学習者は、教材に対応するFlutterプロジェクト内の複数ファイルを編集できる。`lib/main.dart`だけでなく、Widget分割、状態管理、ルーティング、API連携、テストなど、実務に近い構成を扱えるようにする。

ただし、編集対象ファイルを限定しないことと、ビルド環境上で任意のホストファイルや秘密情報へアクセスできることは別である。ファイル編集は、ビルド用ワークスペース内のプロジェクトファイルに閉じる。

### 6.3 ファイルツリー表示

システムは、教材に対応するプロジェクトのファイルツリーを表示できる。

学習者は、ファイルツリーからファイルを選択し、エディタで内容を編集できる。

### 6.4 初期プロジェクト表示

システムは、教材ごとに定義された初期プロジェクトをエディタに表示できる。

学習者は、初期プロジェクトを編集して課題に取り組む。

### 6.5 コード状態の保持

MVPでは、コードはブラウザ上に保存する。

画面遷移、リロード、ビルド実行のたびに不用意に編集中コードが消えないよう、ブラウザのローカルストレージ、IndexedDBなどを利用してプロジェクト状態を保持する。

将来的には、ユーザーごとの進捗、コード履歴、提出履歴、GitHub連携によるリポジトリ保存を検討する。

### 6.6 ローカルダウンロード

学習者は、現在のプロジェクト全体をローカルにダウンロードできる。

MVPでは、プロジェクトファイル一式をZIPなどの形式でエクスポートできることを想定する。

### 6.7 ローカルアップロード

学習者は、ローカルに保存したプロジェクトファイルをアップロードし、ブラウザ上の編集状態として復元できる。

MVPでは、過去に本アプリからダウンロードしたZIP、または所定の構成を満たすプロジェクトファイルを対象とする。

### 6.8 初期状態へのリセット

学習者は、破壊的な変更や復旧困難な編集をしてしまった場合に、教材が定義する初期状態へ戻せる。

リセット機能では、少なくとも次の操作を提供する。

- 現在開いているファイルを初期状態に戻す
- プロジェクト全体を初期状態に戻す

リセットは破壊的な操作であるため、実行前に確認を表示する。将来的には、直前状態の一時退避や履歴からの復元も検討する。

### 6.9 GitHub連携

MVPではGitHub連携は必須としない。

将来的には、学習者のコードをGitHubリポジトリに保存する、GitHubからプロジェクトをインポートする、学習履歴をコミットとして残すなどの連携を検討する。

## 7. サーバービルド

### 7.1 実行方式

MVPでは、Flutterコードの実行方式としてサーバービルド方式を採用する。

学習者がビルドを実行すると、サーバー側でビルド用ワークスペースを作成し、教材に対応するFlutterプロジェクト構成と学習者が編集したプロジェクトファイルを反映したうえでFlutter Webビルドを実行する。

この方式では、ブラウザ上で単純にテンプレート文字列を差し替えて実行するのではなく、サーバー側の制御された環境でFlutter SDKを用いてビルドする。

第一段階では、サーバー側とはユーザーのローカルマシン上で動作するDockerコンテナを指す。第二段階では、クラウド上に生成される一時的なワークスペースまたはコンテナを指す。

### 7.2 ビルド要求

システムは、学習者の操作によりビルド要求を作成できる。

ビルド要求には、少なくとも次の情報を含める。

- 教材ID
- 対象言語またはフレームワーク
- プロジェクトファイル一式
- ビルド設定

### 7.3 ワークスペース生成

サーバーは、ビルド要求ごとに一時的なワークスペースを生成する。

ワークスペースには、教材に対応するプロジェクト構成、固定された依存関係、学習者が編集したプロジェクトファイル一式を配置する。

ビルド終了後、ワークスペースは削除または一定時間後に破棄する。

### 7.4 Flutter Webビルド

サーバーは、生成したワークスペース上でFlutter Webビルドを実行する。

MVPでは、次のような処理を想定する。

```text
flutter pub get
flutter build web
```

開発中の検証では、必要に応じて`flutter run -d web-server`相当の方式も検討する。ただし、学習者に返す成果物は、制御されたサーバー側処理の結果として扱う。

### 7.5 ビルド結果

システムは、ビルド成功または失敗の状態を返す。

ビルド結果には、少なくとも次の情報を含める。

- ビルドステータス
- 標準出力ログ
- 標準エラーログ
- エラー種別
- プレビュー用URLまたは成果物パス

## 8. プレビュー

### 8.1 実行結果表示

システムは、ビルドに成功したFlutter Web成果物をプレビュー画面に表示できる。

MVPでは、同一画面内のプレビュー領域またはiframeで表示することを想定する。

### 8.2 プレビュー更新

学習者がコードを変更して再ビルドした場合、プレビューは最新のビルド結果に更新される。

ビルド失敗時は、前回成功したプレビューを残すか、失敗状態を表示する。どちらを採用するかはUI設計時に決定する。

## 9. ログ表示

### 9.1 ビルドログ表示

システムは、ビルド実行時のログを画面に表示できる。

ログには、標準出力、標準エラー、ビルドステータスを含める。

### 9.2 エラー表示

システムは、ビルド失敗時にエラー内容を確認できるように表示する。

MVPでは、FlutterやDartのエラーを完全に構造化することは必須としない。ただし、学習者が原因を確認できる粒度でログを表示する。

## 10. LLM質問

### 10.1 質問入力

システムは、学習者が教材やコードについてLLMに質問できる入力欄を提供する。

### 10.2 コンテキスト連携

LLMへの問い合わせには、少なくとも次の情報を含める。

- 教材本文
- 学習目標
- 現在のコード
- ビルドログ
- エラーログ
- ユーザーの質問

### 10.3 回答表示

システムは、LLMからの回答を画面に表示する。

回答は、教材の文脈に沿った説明、エラー原因の候補、修正方針を含むことを目指す。

MVPでは、自動修正や自動コード反映は必須としない。

## 11. 対象外機能

MVPでは、次の機能は対象外とする。

- ユーザー登録
- ログイン
- 課金
- 複数ユーザー利用
- 教材販売
- 複数管理者の権限管理
- 本格的な承認ワークフロー
- コード提出と採点
- 進捗管理
- チーム学習機能
- モバイルアプリ提供

## 12. 将来拡張

MVP後に、次の機能を検討する。

- ユーザーごとの進捗保存
- コード履歴保存
- GitHub連携
- 教材のreview状態管理
- 複数人によるAdmin承認フロー
- AIによる教材品質チェック
- AIによる教材修正案の差分表示
- テスト実行
- 採点機能
- Flutter以外の言語、フレームワーク対応
