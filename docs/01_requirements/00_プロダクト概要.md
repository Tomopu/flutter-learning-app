- Flutterを実践的に学ぶためのWebベース学習プラットフォームを作る。
- 教材閲覧、コード編集、サーバービルド、プレビュー、ログ確認、LLM質問を統合する。

## 1. プロダクト名

## 2. 背景

現在、Flutterを学習するための教材は書籍、公式ドキュメント、Web記事、動画教材など多数存在する。しかし、それらの多くはFlutterの基本文法、Widgetの使い方、簡単な画面構築に重点が置かれており、実務的な開発に必要な設計、状態管理、API連携、エラーハンドリング、テスト、ビルド、デプロイ、保守性の高いコード構成までを一貫して学べる教材は多くない。

また、学習者は教材を読み、ローカル環境でコードを書き、エラーを調べ、実行結果を確認し、わからない点を別のツールで質問する必要がある。このように、学習体験が複数のツールに分断されているため、初学者から中級者へ進む段階で学習コストが高くなりやすい。

そこで、教材閲覧、コード編集、実行結果確認、ビルドログ確認、LLMへの質問を1つのWebアプリ上で行える、実践的なFlutter学習環境を開発する。

## 3. 解決したい課題

本プロダクトで解決したい課題は、Flutter学習における「教材」と「実践環境」の分断である。

既存の学習方法では、教材を読む場所、コードを書く場所、実行する場所、エラーを調査する場所、質問する場所が分かれている。そのため、学習者はFlutterそのものだけでなく、環境構築、依存関係管理、エラー調査、検索、質問文の作成などにも多くの時間を使う必要がある。

また、既存教材では実務に近い設計判断や開発フローが十分に扱われない場合がある。たとえば、状態管理の選定、Widget分割、API通信、テスト、ディレクトリ構成、エラーハンドリング、コードレビュー観点などは、実際の開発では重要であるにもかかわらず、初学者向け教材では断片的に扱われることが多い。

本プロダクトでは、教材と実行環境を統合することで、Flutterの実践的な開発を段階的に学習できる環境を提供する。

## 4. プロダクトの目的

本プロダクトの目的は、Flutterを学ぶ開発者が、実務に近い開発体験を通じて、モダンで実践的なFlutter開発を習得できる学習環境を提供することである。

単に文法やWidgetの使い方を学ぶだけではなく、実際のアプリケーション開発で必要となる設計、実装、実行、デバッグ、質問、修正の流れを一体化した学習体験を目指す。

初期段階では個人利用を前提とし、外部公開や商用展開は目的としない。ただし、将来的にはFlutter以外の言語やフレームワークにも拡張できるよう、プロダクト設計は特定の技術に依存しすぎない形にする。

## 5. 提供価値

本プロダクトは、学習者に対して次の価値を提供する。

- 教材を読みながら、同じ画面上でコードを書ける
- コードの実行結果やビルドログを即座に確認できる
- エラーや不明点について、現在の教材内容やコードを踏まえてLLMに質問できる
- 実務に近い構成のFlutter教材を段階的に学習できる
- 第一段階ではローカルDocker上で学習環境を完結させ、第二段階ではクラウド上のサーバービルド環境へ拡張できる
- 将来的には、複数言語・複数フレームワークに対応した実践型学習基盤として拡張できる

## 6. 想定ユーザー

初期段階での想定ユーザーは、Flutterの基礎を学んだ後、より実践的な開発を学びたい開発者である。

具体的には、次のようなユーザーを想定する。

- Flutterの基本的なWidgetやDart文法はある程度理解している人
- 実際にアプリを作ろうとすると、設計や状態管理で詰まる人
- ローカル環境構築やエラー対応に時間を取られやすい人
- 書籍や動画だけではなく、実際に手を動かしながら学びたい人
- LLMを使って学習したいが、教材やコードと連動した質問体験がほしい人

初期利用者は開発者本人を中心とする。将来的に他者へ提供する場合は、ユーザー管理、教材公開管理、進捗管理、セキュリティ、課金、運用体制などを別途検討する。

## 7. 初期スコープ

初期スコープでは、Flutter教材に特化したWeb学習環境を開発する。

最初のMVPでは、次の機能を実現する。

- 教材一覧を表示する
- 教材詳細を表示する
- 教材本文をMarkdown形式で表示する
- コードエディタ上でFlutterコードを編集する
- プロジェクト内の複数ファイルを編集する
- コードをブラウザ上に保存する
- プロジェクト全体をローカルへダウンロードする
- ローカルからプロジェクト全体をアップロードする
- ファイル単位またはプロジェクト単位で初期状態へリセットする
- 模範解答をMarkdown形式で確認する
- 編集したコードをサーバー側のビルド用ワークスペースに反映する
- サーバー側でFlutter Webとしてビルドする
- 実行結果をプレビュー画面に表示する
- ビルドログやエラーログをコンソール風UIに表示する
- 現在の教材内容、コード、エラーログをもとにLLMへ質問できる
- 管理者向け画面から教材を追加・編集する
- 管理者向け画面で教材を複数選択し、公開、非公開、削除を一括実行する
- 教材にプログラミング言語ラベルを付与し、ラベルで絞り込み・並び替えする
- LLMを使って到達目標と成果物からロードマップを作成し、各ステップの教材下書きを生成する
- LLMを使って既存教材の修正案を生成する

初期段階では、ユーザー登録、課金、複数ユーザー対応、本格的な教材販売機能、完全なオンラインIDE機能は対象外とする。

## 8. 将来的な拡張方針

本プロダクトは初期段階ではFlutterに特化するが、将来的には他の言語やフレームワークにも対応できるようにする。

想定される拡張対象は、次の通りである。

- JavaScript
- TypeScript
- React
- Next.js
- Python
- Go
- Webフロントエンド基礎
- バックエンドAPI開発
- データベース連携
- テスト・CI/CD教材

そのため、ドメインモデルはFlutter専用にしない。中心概念は、FlutterLessonやFlutterCourseではなく、Language、Course、Lesson、Exercise、RuntimeEnvironmentとして設計する。

Flutterは、最初に対応する言語・フレームワークの1つとして扱う。

## 9. 教材生成・修正・承認の方針

教材は、初期段階ではMarkdown形式で管理する。教材本文、初期コード、模範解答、メタデータをファイルとして管理し、GitHub上で変更履歴を追えるようにする。

MVPの段階から、AIによる教材生成を取り入れる。AIが教材を生成する場合は、個別教材を独立して直接作るのではなく、まず到達目標と成果物を定義し、その成果物に到達するまでのロードマップを細かいステップに分割する。そのうえで、各ステップに対応する教材を生成する。

AIが生成したロードマップと教材は、そのまま公開せず、必ずdraftとして保存する。人間が内容を確認し、必要に応じて修正したうえで、Admin画面から公開状態に変更したものだけを学習者向けに表示する。

また、教材に誤りが見つかった場合は、修正案を作成し、Adminが承認した段階で公開中の教材に反映する。これにより、教材の品質を保ちながら、継続的に改善できる仕組みを作る。

MVPでは、Admin画面からLLMによる教材修正案を生成できるようにする。ただし、修正案の自動反映は行わず、人間が確認したうえで手動反映する。

公開済み教材と編集中教材は明確に分離する。教材にはバージョンを持たせ、過去の変更履歴を追跡できるようにする。

## 10. 初期開発における重要な技術課題

初期開発において最も重要な技術課題は、Webアプリ上でFlutterコードをどのようにサーバー側でビルドし、その結果を安全に表示するかである。

FlutterはHTML、CSS、JavaScriptのように単純にブラウザ上で直接実行できるわけではない。そのため、MVPではサーバー側にFlutter SDKを含むビルド環境を用意し、ビルド要求ごとに制御されたワークスペースを生成してFlutter Webビルドを実行する方式を採用する。

MVPの段階から、単純なテンプレート文字列差し替え方式ではなく、サーバービルド方式を前提とする。教材ごとの初期プロジェクト構成と依存関係をもとに、ユーザーが編集したプロジェクトファイル一式をビルド用ワークスペースに反映したうえでビルドする。

MVPでは、ユーザーが編集できるファイルを限定しない。`lib/main.dart`だけでなく、複数ファイルのWidget分割、状態管理、ルーティング、API連携、テストなど、実務に近いプロジェクト構成を扱えるようにする。

一方で、ビルド環境は隔離し、編集できる範囲はビルド用ワークスペース内のプロジェクトファイルに閉じる。破壊的な変更をした場合に備えて、ファイル単位またはプロジェクト単位で教材の初期状態へ戻す機能を用意する。

MVPは2段階で進める。第一段階では、フロントエンド、バックエンド、データベース、ビルド実行環境をすべてユーザーのローカルDocker上で動作させるアプリケーション方式とする。第二段階では、GCP、AWSなどのクラウド上にデプロイし、ビルド要求ごとにサーバー上で一時的なワークスペースまたはコンテナを生成する方式へ拡張する。

## 11. 開発体制

開発人数は2人を想定する。

開発には、Claude Code、Codex、AntigravityなどのAI開発支援ツールを活用する。AIには、ドキュメント作成、Issue分割、実装補助、コードレビュー補助、教材生成補助を担わせる。

ただし、プロダクトの目的、MVPスコープ、アーキテクチャ、教材の正確性、公開判断については人間が責任を持つ。

## 12. 現時点での開発方針

現時点では、次の方針で開発を進める。

- 最初の対象はFlutterに限定する
- ただし、設計は将来的な多言語対応を前提にする
- 教材はMarkdownとメタデータで管理する
- AI生成ロードマップとAI生成教材はdraftとして扱う
- MVPからAdmin画面を実装対象に含める
- Admin画面では教材の手動追加、編集、一括公開状態変更、一括削除、言語ラベル管理、LLMによるロードマップ・教材下書き生成、LLM教材修正案生成を扱う
- Adminによる確認後にpublishedとして反映する設計を想定する
- MVPでは編集対象ファイルを限定しない
- MVPではコードをブラウザ上に保存し、プロジェクト全体のダウンロード・アップロードを扱う
- MVPでは模範解答を確認できるようにするが、コード提出と採点は将来拡張とする
- 将来的にはGitHub連携によるコード保存やインポートを検討する
- MVP第一段階はローカルDocker上で完結するアプリケーション方式とする
- MVP第二段階はクラウド上でワークスペースまたはコンテナを生成する方式とする
- 最初は1つの教材を対象に、教材閲覧、コード編集、ビルド、プレビュー、LLM質問の一連の体験を検証する
- 技術的に最も重要な検証対象は、Flutterコードの実行・ビルド方式である
