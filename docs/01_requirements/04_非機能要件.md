## AI Summary

- 最重要の非機能要件は、ビルド環境隔離、秘密情報保護、ビルドタイムアウト、ワークスペース破棄である。
- MVP第一段階は個人または限定利用を前提とするが、将来の外部公開を妨げない責務分離を行う。
- 高可用性、複数ユーザー運用、本格監視はMVPでは必須ではない。

## 1. 目的

この文書では、Flutter学習アプリのMVPおよび将来拡張を見据えた非機能要件を定義する。

## 2. 前提

- 初期利用者は開発者本人または限られた利用者とする。
- 最初の対象はFlutterとする。
- Flutter Webビルドはサーバー側で実行する。
- MVP第一段階では、ローカルDocker上でアプリケーション本体、DB、ビルド環境を動作させる。
- MVP第二段階では、クラウド上でビルド用ワークスペースまたはコンテナを生成する。
- 外部公開、商用利用、複数ユーザー運用はMVP第一段階の対象外とする。

## 3. セキュリティ

| ID | 優先度 | 要求 |
|----|--------|------|
| NFR-SEC-001 | Must | ビルド環境は、アプリケーション本体、DB、秘密情報から分離されていなければならない。 |
| NFR-SEC-002 | Must | ビルド処理は、ホスト環境の任意ファイルへアクセスできてはならない。 |
| NFR-SEC-003 | Must | 編集可能範囲は、ビルド用ワークスペース内のプロジェクトファイルに限定しなければならない。 |
| NFR-SEC-004 | Must | システムは、APIキー、DB接続情報、LLMプロバイダー認証情報をビルド対象コードへ渡してはならない。 |
| NFR-SEC-005 | Must | システムは、LLMへ秘密情報、APIキー、DB接続情報、ホストパスを送ってはならない。 |
| NFR-SEC-006 | Must | LLM生成教材は自動で `published` にしてはならない。 |
| NFR-SEC-007 | Must | Admin APIは、学習者向けAPIとは別の権限境界として扱わなければならない。 |
| NFR-SEC-008 | Should | アップロードされたプロジェクトファイルは、危険なパス、巨大ファイル、ビルド環境外参照を拒否できることが望ましい。 |

## 4. 信頼性

| ID | 優先度 | 要求 |
|----|--------|------|
| NFR-REL-001 | Must | ビルド処理にはタイムアウトを設定しなければならない。 |
| NFR-REL-002 | Must | ビルド用ワークスペースは、ビルド完了、失敗、タイムアウト後に破棄されなければならない。 |
| NFR-REL-003 | Must | ビルド失敗時、システムはユーザーに失敗状態を表示しなければならない。 |
| NFR-REL-004 | Must | 学習者がプロジェクトを壊した場合でも、初期状態へ復旧できなければならない。 |
| NFR-REL-005 | Should | 一時的な依存取得失敗などに対する限定的なリトライを将来検討できる構造であることが望ましい。 |

## 5. 性能

| ID | 優先度 | 要求 |
|----|--------|------|
| NFR-PERF-001 | Must | ビルド中は、画面上で処理中状態を明確に表示しなければならない。 |
| NFR-PERF-002 | Should | 教材一覧、教材詳細、コードエディタの通常操作では、学習を妨げる待機が目立たないことが望ましい。 |
| NFR-PERF-003 | Must | システムは、同時ビルド数に上限を設けられる設計でなければならない。 |
| NFR-PERF-004 | Should | 初回ビルドと2回目以降のビルド時間を計測し、キャッシュや依存固定の必要性を判断できることが望ましい。 |

## 6. 可用性

| ID | 優先度 | 要求 |
|----|--------|------|
| NFR-AVL-001 | Won't | MVP第一段階では、高可用性構成を必須としない。 |
| NFR-AVL-002 | Should | 将来の外部公開時には、ビルドワーカー分離、キュー、成果物ストレージ、監視、バックアップを検討できることが望ましい。 |

## 7. 保守性

| ID | 優先度 | 要求 |
|----|--------|------|
| NFR-MAINT-001 | Must | 教材、教材編集、ビルド要求、実行環境、LLM質問、LLM教材生成は責務を分離して設計しなければならない。 |
| NFR-MAINT-002 | Must | Flutter固有の処理は実行環境の実装詳細として閉じ、上位の教材モデルはFlutter専用にしすぎてはならない。 |
| NFR-MAINT-003 | Should | ビルド設定、タイムアウト、Flutter SDKバージョン、アップロード制限は設定として管理できることが望ましい。 |
| NFR-MAINT-004 | Must | アプリケーションログとビルドログは区別して扱わなければならない。 |

## 8. 拡張性

| ID | 優先度 | 要求 |
|----|--------|------|
| NFR-EXT-001 | Should | 将来的にFlutter以外の言語やフレームワークを追加できる設計であることが望ましい。 |
| NFR-EXT-002 | Should | 新しい実行環境を追加する際、教材表示やLLM質問機能を大きく変更しない構造であることが望ましい。 |
| NFR-EXT-003 | Should | 教材管理は、将来的な承認フロー、バージョン管理、差分表示へ拡張できることが望ましい。 |
| NFR-EXT-004 | Could | 将来的にGitHub連携によるコード保存やインポートへ拡張できることが望ましい。 |

## 9. ユーザビリティ

| ID | 優先度 | 要求 |
|----|--------|------|
| NFR-UX-001 | Must | 学習画面では、教材、コードエディタ、プレビュー、ログ、LLM質問、模範解答を分断しすぎず配置しなければならない。 |
| NFR-UX-002 | Must | ビルド中、成功、失敗、タイムアウトの状態を画面上で明確に表示しなければならない。 |
| NFR-UX-003 | Must | ビルドエラーは、学習者が原因を確認できる粒度で表示しなければならない。 |
| NFR-UX-004 | Must | リセット操作では、現在の変更が失われることを明確に表示しなければならない。 |
| NFR-UX-005 | Should | ダウンロード操作は、ビルド成果物ではなく現在のプロジェクト一式を保存する操作として分かることが望ましい。 |

## 10. 運用

| ID | 優先度 | 要求 |
|----|--------|------|
| NFR-OPS-001 | Must | MVP第一段階では、ローカルDocker上でアプリ本体、DB、ビルド環境を起動できなければならない。 |
| NFR-OPS-002 | Should | Dockerを利用する場合は、セットアップ手順を文書化することが望ましい。 |
| NFR-OPS-003 | Should | 将来のクラウド化では、認証、認可、ビルドキュー、ワーカー分離、成果物ストレージ、監視、コスト上限を検討できることが望ましい。 |
| NFR-OPS-004 | Could | ビルド失敗率、ビルド時間、タイムアウト回数、LLM問い合わせ失敗率を将来的に計測できることが望ましい。 |

## 11. 品質

| ID | 優先度 | 要求 |
|----|--------|------|
| NFR-QLT-001 | Must | MVPの主要ユースケースに対して、受け入れ基準を定義しなければならない。 |
| NFR-QLT-002 | Must | ビルド要求、ビルド成功、ビルド失敗、LLM質問、Admin教材作成はテスト対象に含めなければならない。 |
| NFR-QLT-003 | Should | 学習者と管理者の主要フローはE2Eテスト対象にすることが望ましい。 |

## 12. 数値目標

MVP第一段階では、厳密なSLOは設定しない。実装後に実測し、必要に応じて数値目標へ昇格する。

| ID | 項目 | 初期目安 |
|----|------|----------|
| MET-001 | ビルドタイムアウト | 30秒から120秒程度で実測調整 |
| MET-002 | 同時ビルド数 | ローカルDockerでは1から2件程度 |
| MET-003 | 画面応答 | 通常操作で待機が目立たないこと |
