# バックエンド設計

## 1. 目的

本ドキュメントは、Flutter学習アプリのMVPにおけるバックエンド実装方針を定義する。

APIのエンドポイント一覧は [API設計](03_API設計.md) で扱う。本ドキュメントでは、バックエンド内部の責務分割、ディレクトリ構成、ビルド実行処理、ファイル検証、LLM連携、エラーハンドリング、ログ、設定管理を扱う。

MVPでは、Node.js、TypeScript、Hono、Prisma、PostgreSQLを前提とする。技術選定の詳細は [技術選定](01_技術選定.md) を参照する。

## 2. 前提

MVP第一段階では、バックエンドAPI、PostgreSQL、Flutter Webビルド環境をローカルDocker上で動作させる。

MVP第二段階では、クラウド上でビルド要求ごとに一時的なワークスペースまたはコンテナを生成する。

MVPでは本格的なユーザー認証は必須としない。ただし、学習者向けAPIと管理者向けAPIはルーティングとサービス層で分離し、将来的に認証・認可を追加できる構成にする。

## 3. バックエンドの責務

バックエンドは、次の責務を持つ。

- 教材、コース、ロードマップ、言語ラベルの取得
- Admin向けの教材作成、編集、公開状態変更、一括操作
- ビルド要求の受付
- ビルド状態とビルド履歴の管理
- ビルドログの保存と取得
- ビルド成果物の参照情報管理
- 初期プロジェクト、参考プロジェクト、アップロードファイルの検証
- 学習者向けLLM質問の仲介
- Admin向けLLMロードマップ生成、教材生成、教材修正案生成の仲介
- LLM生成履歴の保存
- 入力バリデーション、エラーレスポンス、アプリケーションログの管理

バックエンドは、フロントエンドの画面状態やエディタ状態を直接管理しない。MVPでは、学習者の編集中コードはブラウザ上に保存し、ビルド要求時にプロジェクトファイル一式としてバックエンドへ送信する。

## 4. 採用技術

バックエンドで採用する主な技術は次の通りである。

| 領域 | 採用技術 | 用途 |
| --- | --- | --- |
| 実行環境 | Node.js | API、ビルド制御、LLM連携 |
| 言語 | TypeScript | 型安全な実装 |
| APIフレームワーク | Hono | HTTPルーティング |
| DB | PostgreSQL | 教材、ビルド履歴、LLM生成履歴の保存 |
| ORM | Prisma | DBアクセス、マイグレーション |
| バリデーション | Zod | API入力検証 |
| APIドキュメント | OpenAPI / Scalar | API仕様の自動生成と閲覧 |
| テスト | Vitest | サービス、バリデーション、状態遷移のテスト |

Zodは、APIリクエスト、LLM出力、設定値の検証に利用する。Honoのルート定義では、リクエスト本文とクエリパラメータをZodで検証してからService層へ渡す。

API仕様は手書きMarkdownだけに依存しない。HonoのRoute定義とZodスキーマからOpenAPIを生成し、開発中にAPIドキュメントを確認できるようにする。

## 5. ディレクトリ構成

MVPでは、次のような構成を基本とする。

```text
apps/

    src/

      routes/
        learner/
          courses.ts
          lessons.ts
          builds.ts
          llmQuestions.ts
        admin/
          lessons.ts
          languageLabels.ts
          roadmaps.ts
          llmGenerations.ts
      schemas/
        lessonSchemas.ts
        buildSchemas.ts
        llmSchemas.ts
        fileSchemas.ts
      services/
        lessonService.ts
        adminLessonService.ts
        buildService.ts
        llmQuestionService.ts
        llmGenerationService.ts
      repositories/
        lessonRepository.ts
        roadmapRepository.ts
        buildRepository.ts
        llmRepository.ts
      build/
```

実装時の都合で細部は変更してよい。ただし、Route、Schema、Service、Repository、Build、LLM、Filesの責務は混ぜない。

## 6. レイヤー設計

バックエンドは、次のレイヤーに分ける。

| レイヤー | 主な責務 |
| --- | --- |
| Route | HTTPリクエストの受け取り、認可境界、レスポンス整形 |
| Schema | リクエスト、レスポンス、設定値、LLM出力のバリデーション |
| Service | ユースケース実行、状態遷移、複数Repositoryの調整 |
| Repository | Prismaを使ったDBアクセス |
| Build | ワークスペース生成、Flutterビルド実行、成果物管理 |
| Files | パス検証、ZIP入出力、プロジェクト構成検証 |
| LLM | プロンプト生成、Provider API呼び出し、出力検証 |
| Errors | アプリケーションエラー定義、HTTPエラー変換 |
| Logging | アプリケーションログ、ビルドログ、LLM履歴の出力 |

Route層ではビジネスロジックを持たない。Route層は、入力検証、Service呼び出し、HTTPレスポンスへの変換に限定する。

Repository層ではHTTPやLLM、ファイルシステムに依存しない。DBアクセスだけを扱う。

Build層とLLM層は副作用が大きいため、Service層から明示的に呼び出す。

## 7. APIルーティング構成

APIは、次の単位でルーティングを分ける。

```text
/api/courses
/api/lessons
/api/builds
/api/llm/questions
/api/admin/lessons
/api/admin/language-labels
/api/admin/roadmaps
/api/admin/llm
```

学習者向けAPIと管理者向けAPIは、URL、Routeファイル、Serviceを分ける。

MVPでは認証なしでも動作させるが、`/api/admin/*` は将来的にAdmin認可を必ず差し込む前提で実装する。

## 8. APIドキュメント生成

APIドキュメントは、実装と乖離しないようにOpenAPIとして生成する。

MVPでは、次のエンドポイントを提供する。

```text
GET /api/openapi.json
GET /api/docs
```

`/api/openapi.json` は、HonoのRoute定義とZodスキーマから生成したOpenAPI JSONを返す。

`/api/docs` は、ScalarまたはSwagger UIを利用してAPIドキュメントを表示する。UIはMVPでは開発者向けとし、外部公開時にはアクセス制御を検討する。

APIドキュメント生成では、次を対象にする。

- エンドポイント
- HTTPメソッド
- パスパラメータ
- クエリパラメータ
- リクエストボディ
- レスポンスボディ
- HTTPステータス
- エラー形式

API設計ドキュメントは方針と設計意図を管理し、OpenAPIは実装に近いAPI仕様を管理する。

## 9. 入力バリデーション

API入力は、Route層でZodにより検証する。

検証対象は次の通りである。

- パスパラメータ
- クエリパラメータ
- リクエストボディ
- アップロードファイルのメタデータ
- ビルド対象ファイル一覧
- LLM生成リクエスト
- Admin一括操作対象ID

バリデーションで不正な入力を検出した場合は、`400 Bad Request` を返す。

存在しない教材、ビルド、ロードマップ、LLM生成履歴を参照した場合は、`404 Not Found` を返す。

## 10. 教材管理処理

教材管理では、次の処理を扱う。

- 公開済み教材一覧の取得
- 教材詳細の取得
- 初期プロジェクトの取得
- Admin向け教材一覧の取得
- Admin向け教材作成、更新、削除
- 教材の公開状態変更
- 教材の一括公開、一括下書き化、一括削除
- 言語ラベルの作成、取得、紐付け

学習者向けAPIでは、原則として`published`の教材のみを返す。

Admin向けAPIでは、`draft`と`published`の両方を扱う。

LLMが生成した教材は、必ず`draft`として保存する。自動で`published`にしない。

## 11. ビルド実行処理

### 11.1 基本方針

ビルド処理は、バックエンド本体と分離されたワークスペースで実行する。

MVP第一段階では、ローカルDocker上の一時ディレクトリまたはビルド用コンテナでFlutter Webビルドを実行する。

MVP第二段階では、ビルド要求ごとにクラウド上の一時ワークスペースまたはコンテナを生成する。

### 11.2 処理フロー

`POST /api/builds` の処理フローは次の通りである。

1. リクエストをZodで検証する
2. 教材IDの存在を確認する
3. 送信されたファイル一覧を検証する
4. Buildレコードを`queued`で作成する
5. ビルド用ワークスペースを生成する
6. 教材の初期プロジェクトをワークスペースへ展開する
7. 学習者が送信したファイルでワークスペースを更新する
8. Buildレコードを`running`へ更新する
9. Flutter Webビルドを実行する
10. stdout、stderr、systemログをBuildLogとして保存する
11. 成果物をプレビュー用ディレクトリへ配置する
12. Buildレコードを`succeeded`、`failed`、`timeout`のいずれかへ更新する
13. 不要なワークスペースを削除する

MVP第一段階では同期処理として実装してもよい。ただし、Buildレコードの状態遷移はキュー化を想定して設計する。

### 11.3 Build状態

Build状態は次を扱う。

- `queued`
- `running`
- `succeeded`
- `failed`
- `timeout`
- `cancelled`

状態遷移はService層で管理し、Route層やBuildRunnerが直接DB状態を自由に変更しない。

### 11.4 タイムアウト

ビルド処理にはタイムアウトを設ける。

MVPの初期値は、実際のFlutter Webビルド時間を測定して調整する。初期目安は30秒から120秒程度とする。

タイムアウト時は、実行中プロセスを停止し、Build状態を`timeout`に更新する。

## 12. ファイル検証

プロジェクトファイルの検証では、次を必須とする。

- `..` を含むパスを拒否する
- 絶対パスを拒否する
- 空のパスを拒否する
- ファイル数上限を設ける
- 1ファイルあたりのサイズ上限を設ける
- 合計サイズ上限を設ける
- `pubspec.yaml` が存在することを確認する
- `lib/` 配下のファイルが存在することを確認する
- ビルド用ワークスペース外へ書き込まない

MVPの目安は、1ファイルあたり1MB、合計50MB、ファイル数500件とする。

巨大な動画、不要なバイナリ、秘密情報らしきファイルはMVPでは拒否または警告対象とする。

## 13. ファイル入出力

初期プロジェクト、参考プロジェクト、ビルド入力、ビルド成果物は、参照先をDBに保存する。

MVP第一段階では、ローカルボリューム上のパスまたはキーを保存する。

MVP第二段階では、オブジェクトストレージのキーへ置き換える。

バックエンドAPIは、任意のローカルファイルパスを直接返さない。成果物やプロジェクトファイルを返す場合は、許可された保存領域のキーから解決する。

## 14. LLM連携

### 14.1 基本方針

LLM連携は、Provider APIを直接Route層から呼ばない。

LLM連携は、`LlmClient`、`PromptBuilder`、`LlmGenerationService`、`LlmQuestionService` に分ける。

| コンポーネント | 主な責務 |
| --- | --- |
| LlmClient | Provider API呼び出し |
| PromptBuilder | 教材、コード、ログからプロンプトを組み立てる |
| LlmQuestionService | 学習者質問のユースケース |
| LlmGenerationService | ロードマップ、教材、修正案生成のユースケース |

### 14.2 学習者質問

学習者質問では、少なくとも次をコンテキストとして扱う。

- 教材本文
- 学習目標
- 現在のコード
- ビルドログ
- エラーログ
- ユーザーの質問

秘密情報、APIキー、DB接続情報、ホストパスはLLMへ送らない。

### 14.3 Admin向けLLM生成

Admin向けLLM生成では、次を扱う。

- ロードマップ生成
- 教材生成
- 教材修正案生成

LLM生成結果は`LlmGeneration`として保存し、教材やロードマップとして採用する場合も`draft`から開始する。

LLM出力はZodなどで構造検証を行う。検証できない出力は、自動保存または自動反映しない。

## 15. エラーハンドリング

バックエンドでは、アプリケーションエラーを共通形式で扱う。

レスポンス例は次の通りである。

```json
{
  "error": {
    "code": "BUILD_TIMEOUT",
    "message": "Build timed out.",
    "details": {}
  }
}
```

主なエラー種別は次の通りである。

| HTTPステータス | 用途 |
| --- | --- |
| 400 | 入力不正、ファイル検証エラー |
| 404 | 教材、ビルド、ロードマップ、生成履歴が存在しない |
| 409 | 状態遷移不正、重複操作 |
| 413 | アップロードサイズ超過 |
| 429 | 将来のレート制限 |
| 500 | 想定外のサーバーエラー |
| 502 | LLM Providerまたは外部サービスの失敗 |
| 504 | ビルドまたはLLM処理のタイムアウト |

学習者向けレスポンスには、秘密情報、ホストパス、内部スタックトレースを含めない。

## 16. ログ設計

ログは、次の3種類に分ける。

### 16.1 アプリケーションログ

APIリクエスト、エラー、状態遷移、外部API呼び出し結果を記録する。

アプリケーションログには、APIキー、DB接続文字列、秘密情報、送信されたコード全文を不用意に出力しない。

### 16.2 ビルドログ

Flutter Webビルドのstdout、stderr、systemログをBuildLogとして保存する。

学習者に表示するログと、運用者向けの内部ログは分けられる設計にする。

### 16.3 LLM生成履歴

LLM生成では、入力概要、出力、生成種別、対象教材またはロードマップ、状態を保存する。

秘密情報や不要なホスト情報は保存しない。

## 17. 設定管理

設定値は環境変数と設定モジュールで管理する。

主な設定値は次の通りである。

- `DATABASE_URL`
- `LLM_API_KEY`
- `LLM_MODEL`
- `BUILD_WORKSPACE_ROOT`
- `BUILD_ARTIFACT_ROOT`
- `BUILD_TIMEOUT_SECONDS`
- `BUILD_MAX_CONCURRENCY`
- `UPLOAD_MAX_FILE_SIZE`
- `UPLOAD_MAX_TOTAL_SIZE`
- `UPLOAD_MAX_FILE_COUNT`
- `FLUTTER_SDK_VERSION`
- `NODE_ENV`

設定値は起動時に検証する。必須設定が不足している場合は、サーバー起動時に失敗させる。

## 18. セキュリティ境界

バックエンドでは、次の境界を守る。

- 学習者向けAPIとAdmin APIを分離する
- ビルド環境をアプリケーション本体から分離する
- ビルド用ワークスペース外への読み書きを禁止する
- 秘密情報をビルド環境へ渡さない
- 秘密情報をLLMへ送らない
- LLM生成教材を自動公開しない
- アップロードファイルのパスとサイズを検証する
- 外部公開時にはAdmin認証と認可を必須にする

セキュリティ方針の詳細は [セキュリティ方針](02_セキュリティ方針.md) を参照する。

## 19. テスト方針

MVPで優先するバックエンドテストは次の通りである。

- API入力バリデーション
- OpenAPI生成対象のルート定義
- ファイルパス検証
- アップロード上限検証
- Build状態遷移
- BuildRunnerの成功、失敗、タイムアウト
- LLMプロンプト生成
- LLM出力検証
- 教材の`draft`、`published`制御

ビルド実行そのものは環境依存が大きいため、ユニットテストではBuildRunnerをモック化し、Docker上の結合テストで実ビルドを確認する。

## 20. 将来拡張

将来拡張では、次を差し替えまたは追加できるようにする。

- 認証、認可をRoute層またはMiddlewareに追加する
- ビルド要求をキューへ投入し、BuildWorkerで非同期実行する
- ローカル成果物保存をS3またはCloud Storageへ差し替える
- ローカルワークスペース生成をCloud Run Jobs、ECS Tasks、Kubernetes Jobsへ差し替える
- Redisを使ってビルドキュー、レート制限、短期キャッシュを管理する
- Pythonワーカーを追加し、教材解析、コード解析、評価処理を分離する
- Flutter以外の実行環境をRuntimeEnvironmentとして追加する

MVPでは、これらを最初から実装しない。ただし、Service層、Build層、LLM層、Repository層を分離し、後から差し替えられる構造にしておく。
