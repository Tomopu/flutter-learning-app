# DB設計

## 1. 目的

本ドキュメントは、Flutter学習アプリのMVPで必要となるデータベース設計方針を定義する。

MVPでは、教材、ロードマップ、教材ステップ、プログラミング言語ラベル、ビルド履歴、LLM生成履歴を扱える構成にする。

## 2. 前提

MVP第一段階では、ローカルDocker上のデータベースを利用する。

MVP第二段階では、クラウド環境のマネージドDBまたはコンテナ上のDBを検討する。

コード本体はMVPではブラウザ上に保存し、必要に応じてプロジェクト全体をダウンロード・アップロードする。サーバー側DBでは、教材の初期プロジェクト、参考プロジェクト、メタデータ、ビルド履歴、LLM生成履歴を管理する。

## 3. 中心エンティティ

MVPで扱う中心エンティティは次の通りである。

- Course
- Lesson
- Roadmap
- RoadmapStep
- LanguageLabel
- LessonLanguageLabel
- Build
- BuildLog
- LlmGeneration
- LlmQuestion

## 4. Course

Courseは、複数の教材をまとめるカテゴリ的な単位である。RoadmapとCourseは完全に独立した概念として扱う。CourseはLessonのグループ分けを担い、RoadmapはLLM生成によるカリキュラムパスを表す。1つのLessonは複数のRoadmapに登場しても構わない。

主な項目は次の通りである。

- `id`
- `title`
- `description`
- `level`（`beginner` / `intermediate` / `advanced`）
- `status`（`draft` / `published`）
- `createdAt`
- `updatedAt`

MVPではCourseを簡易的に扱い、Lesson中心で実装してもよい。

## 5. Lesson

Lessonは、学習者が閲覧・実行する教材の単位である。

主な項目は次の通りである。

- `id`
- `courseId`（NULL許容。CourseなしでLessonを作成できる）
- `llmGenerationId`（NULL許容。LLMで生成されたLessonの場合、元のLlmGenerationレコードへの参照。手動作成の場合はNULL）
- `order`（Course内での表示順。courseIdがNULLの場合は未使用）
- `title`
- `description`
- `level`（`beginner` / `intermediate` / `advanced`）
- `bodyMarkdown`
- `learningGoals`（学習目標をMarkdownまたは文字列で保持）
- `initialProjectRef`（初期プロジェクトのストレージパス/キー。MVP第一段階はローカルボリューム、第二段階はオブジェクトストレージ）
- `solutionProjectRef`（参考プロジェクトのストレージパス/キー。同上）
- `status`
- `createdAt`
- `updatedAt`

`status`はMVPでは少なくとも次を扱う。

- `draft`
- `published`

`review`はMVPでは任意とし、複数人レビューが必要になった段階で追加する。

## 6. Roadmap

Roadmapは、到達目標と成果物に向かう学習ステップ全体を表す。

主な項目は次の通りである。

- `id`
- `title`
- `goal`
- `finalDeliverable`
- `targetLevel`（`beginner` / `intermediate` / `advanced`）
- `status`
- `createdAt`
- `updatedAt`

`status`はLessonと同様に少なくとも次を扱う。

- `draft`
- `published`

LLMで生成したRoadmapは自動公開せず、`draft`として保存する。

## 7. RoadmapStep

RoadmapStepは、Roadmapを細かく分割した各ステップを表す。

主な項目は次の通りである。

- `id`
- `roadmapId`
- `lessonId`
- `order`
- `title`
- `goal`
- `intermediateDeliverable`
- `createdAt`
- `updatedAt`

`lessonId`はNULL許容とする。Roadmap生成直後はLessonがまだ存在しない場合があるため、後からLessonと紐付ける運用を想定する。

各RoadmapStepは、最終的に対応するLessonを持つことを想定する。

## 8. LanguageLabel

LanguageLabelは、教材に付与するプログラミング言語名またはフレームワーク名のラベルである。

主な項目は次の通りである。

- `id`
- `name`
- `slug`
- `createdAt`
- `updatedAt`

例は次の通りである。

- Flutter
- Dart
- JavaScript
- TypeScript
- React
- Next.js
- Python
- Go

## 9. LessonLanguageLabel

LessonLanguageLabelは、LessonとLanguageLabelの中間テーブルである。

主な項目は次の通りである。

- `lessonId`
- `languageLabelId`

1つの教材に複数のラベルを付与できるようにする。

## 10. Build

Buildは、学習者が実行したビルド要求と結果を表す。

主な項目は次の通りである。

- `id`
- `lessonId`
- `inputRef`（ビルド時に送信されたプロジェクトのストレージパス/キー。LLM質問やデバッグ時に参照する）
- `status`
- `startedAt`
- `finishedAt`
- `previewUrl`
- `artifactRef`
- `createdAt`
- `updatedAt`（status遷移の追跡に使用）

`status`は次を想定する。

- `queued`
- `running`
- `succeeded`
- `failed`
- `timeout`
- `cancelled`

MVP第一段階では、ビルド履歴の永続保存は簡易的でよい。ただし、ビルドログ表示とLLM質問への連携に必要な情報は保持する。

将来のユーザー管理導入時に`userId`カラムを追加することを想定しておく。

## 11. BuildLog

BuildLogは、ビルド時のログを表す。

主な項目は次の通りである。

- `id`
- `buildId`
- `type`
- `content`
- `createdAt`

`type`は次を想定する。

- `stdout`
- `stderr`
- `system`

## 12. LlmGeneration

LlmGenerationは、LLMによるロードマップ生成、教材生成、教材修正案生成の履歴を表す。

主な項目は次の通りである。

- `id`
- `type`
- `input`
- `output`
- `status`
- `targetLessonId`
- `targetRoadmapId`
- `createdAt`

`type`は次を想定する。

- `roadmap_generation`
- `lesson_generation`
- `lesson_revision`

`status`は次を想定する。

- `pending`（処理中）
- `completed`（正常完了）
- `failed`（エラーで終了）

## 13. LlmQuestion

LlmQuestionは、学習者が教材・コード・ログについて質問した履歴を表す。

主な項目は次の通りである。

- `id`
- `lessonId`
- `buildId`（NULL許容。ビルド結果に対する質問の場合に設定する）
- `question`（学習者が入力した質問文）
- `context`（質問時のコンテキスト情報: 現在のコード、ビルドログ、エラーログをJSONで保持）
- `answer`（LLMが返した回答）
- `createdAt`

MVPでは永続保存は必須ではないが、デバッグや品質改善のために保存できる設計にしておく。

## 14. 削除方針

MVPでは、Admin画面から教材を削除できる。

削除は破壊的な操作であるため、UIで確認を行う。DB設計としては、将来的な復旧や監査を考慮し、物理削除ではなく論理削除を検討する。

MVPでは実装容易性を優先し、物理削除から開始してもよい。ただし、外部公開や複数管理者運用を行う段階では論理削除に移行する。
