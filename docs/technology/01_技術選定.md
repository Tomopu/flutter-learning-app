# 技術選定

## 1. 目的

本ドキュメントは、Flutter学習アプリのMVPで採用する技術スタックと、その選定理由を定義する。

MVPでは、教材閲覧、コード編集、サーバー側Flutter Webビルド、プレビュー、ビルドログ表示、LLM質問、Admin教材管理を1つのWebアプリとして成立させることを優先する。

技術選定では、第一段階のローカルDockerアプリケーション方式を素早く実装できること、第二段階のクラウドサーバービルド方式へ拡張できること、将来的な多言語対応を妨げないことを重視する。

## 2. 前提

MVPは次の2段階で進める。

### 2.1 第一段階: ローカルDockerアプリケーション方式

第一段階では、フロントエンド、バックエンド、データベース、ビルド実行環境をローカルDocker上で動作させる。

この段階では、外部公開や複数ユーザー利用よりも、教材閲覧、コード編集、ビルド、プレビュー、LLM質問、教材管理の一連の体験をローカルで安定して動かすことを優先する。

### 2.2 第二段階: クラウドサーバービルド方式

第二段階では、GCP、AWSなどのクラウド上にアプリケーションをデプロイし、ビルド要求ごとに一時的なワークスペースまたはコンテナを生成する。

この段階では、認証、認可、ビルドキュー、リソース制限、成果物ストレージ、監視、コスト管理を追加で検討する。

## 3. 採用技術一覧

MVP第一段階での採用技術は次の通りである。

| 領域 | 採用技術 | 用途 |
| --- | --- | --- |
| フロントエンド | Next.js | ReactベースのWebアプリケーション基盤 |
| 言語 | TypeScript | フロントエンド、バックエンド共通の型安全性 |
| スタイリング | CSS Modules / 純CSS | UI実装と共通スタイル管理 |
| コードエディタ | Monaco Editor | ブラウザ上のコード編集 |
| バックエンド | Node.js | API、ビルド制御、LLM連携 |
| APIフレームワーク | Hono | 軽量なHTTP API実装 |
| データベース | PostgreSQL | 教材、ビルド履歴、LLM生成履歴の保存 |
| ORM | Prisma | DBスキーマ管理と型安全なDBアクセス |
| 実行環境 | Docker | アプリケーション、DB、ビルド環境のローカル起動 |
| ビルド環境 | Flutter SDK | Flutter Webビルド |
| LLM連携 | LLM Provider API | 学習者質問、教材生成、教材修正案生成 |
| パッケージ管理 | pnpm | Node.jsパッケージ管理 |
| 品質管理 | ESLint / Prettier | 静的解析、フォーマット |
| テスト | Vitest / Playwright | ユニットテスト、主要画面のE2Eテスト |

## 4. フロントエンド

### 4.1 Next.js

フロントエンドにはNext.jsを採用する。

採用理由は次の通りである。

- ReactベースでUIを構築できる
- 教材一覧、学習画面、Admin画面をページ単位で整理しやすい
- TypeScriptとの相性がよい
- 将来的にAPI境界や認証を追加しやすい
- ローカルDocker、クラウド環境のどちらでも運用しやすい

MVPでは、画面表示とAPI呼び出しを明確に分ける。サーバービルドやLLM連携などの副作用が大きい処理は、フロントエンド内に閉じ込めず、バックエンドAPI経由で実行する。

### 4.2 Reactの扱い

UI実装は、Next.jsが前提とするReactコンポーネントとして実装する。

ReactをNext.jsとは別の独立した技術選定項目として扱うのではなく、Next.jsによる画面実装の基盤として扱う。

教材表示、ファイルツリー、コードエディタ、プレビュー、ログビュー、LLMチャット、Admin編集画面など、状態を持つ画面部品はReactコンポーネントとして分割する。

### 4.3 TypeScript

フロントエンドとバックエンドの実装言語にはTypeScriptを採用する。

教材、ビルド要求、ビルド状態、LLM質問、Admin操作などのデータ構造を型として扱い、API境界での不整合を減らす。

### 4.4 CSS Modules / 純CSS

スタイリングにはCSS Modulesまたは純CSSを採用する。

MVPでは、Tailwind CSSを前提にしない。学習画面、Admin画面、コードエディタ、ログ表示、プレビューなど、UIの責務が比較的明確であるため、CSS Modulesまたは純CSSで十分に実装できる。

UIが一貫しなくなることを避けるため、色、余白、文字サイズ、ボタン、入力欄、パネル、ログ表示などの基本スタイルはCSS変数と共通クラスで管理する。

コンポーネント固有のスタイルは、Next.jsのCSS Modulesを優先する。画面全体に関わるリセット、テーマ変数、基本タイポグラフィはグローバルCSSで管理する。

### 4.5 Monaco Editor

ブラウザ上のコードエディタにはMonaco Editorを採用する。

採用理由は次の通りである。

- 複数ファイル編集に向いたエディタ体験を提供できる
- Dart、JSON、YAML、Markdownなど複数形式の表示に対応しやすい
- ファイルツリー、タブ、ログ表示と組み合わせやすい
- 将来的な補完、診断表示、差分表示へ拡張しやすい

MVPでは、完全なオンラインIDEを目指さない。主な目的は、教材に対応するFlutterプロジェクトのファイルを編集し、ビルドへ渡せる状態を作ることである。

## 5. バックエンド

### 5.1 Node.js

バックエンドにはNode.jsを採用する。

採用理由は次の通りである。

- フロントエンドと同じTypeScriptで実装できる
- API型、バリデーション、ドメイン型を共有しやすい
- Docker上で扱いやすい
- ビルド制御、ファイル操作、LLM API連携を実装しやすい
- 小規模MVPでフロントエンドとバックエンドの開発体験を揃えやすい

MVPでは、Node.jsバックエンドが教材API、Admin API、ビルド要求API、LLM連携APIを提供する。

### 5.2 Hono

APIフレームワークにはHonoを採用する。

採用理由は次の通りである。

- 軽量でMVP実装に向いている
- ルーティングが簡潔で、APIの責務分離を表現しやすい
- TypeScriptとの相性がよい
- 将来的に実行環境を変更する場合でも移植しやすい

APIは、学習者向け、管理者向け、ビルド実行、LLM連携で責務を分ける。詳細は [API設計](03_API設計.md) を参照する。

### 5.3 FastAPIを主軸にしない理由

FastAPIは、PythonでLLM連携やデータ処理を行う場合に有力な候補である。

ただし、MVPではフロントエンドとバックエンドをTypeScript中心で揃え、実装速度と型共有を優先するため、主軸にはしない。

将来的にPython製の教材解析、コード解析、LLM評価、バッチ処理が必要になった場合は、バックエンド本体とは分離したワーカーまたは補助サービスとしてFastAPIやPythonスクリプトを追加する。

## 6. データベース

### 6.1 PostgreSQL

データベースにはPostgreSQLを採用する。

採用理由は次の通りである。

- 教材、ロードマップ、ビルド履歴、LLM生成履歴をリレーショナルに扱いやすい
- JSON型を利用して、LLM入出力や教材メタデータのような柔軟なデータも保存できる
- Docker上で動かしやすい
- 将来的にマネージドDBへ移行しやすい

DB設計の詳細は [DB設計](04_DB設計.md) を参照する。

### 6.2 Prisma

ORMにはPrismaを採用する。

採用理由は次の通りである。

- TypeScriptから型安全にDBアクセスできる
- スキーマとマイグレーションを管理しやすい
- MVPのスキーマ変更に追従しやすい
- PostgreSQLとの相性がよい

MVPでは、教材、ロードマップ、ビルド、LLM生成履歴をPrismaスキーマで管理する。

## 7. ビルド実行環境

### 7.1 Docker

ローカル実行環境にはDockerを採用する。

採用理由は次の通りである。

- フロントエンド、バックエンド、DB、ビルド環境を同じ手順で起動できる
- Flutter SDKを含むビルド環境をアプリケーション本体から分離できる
- 将来的なクラウドコンテナ実行へつなげやすい
- ビルド環境の依存関係を固定しやすい

MVP第一段階では、Docker Composeで次のサービスを起動する想定とする。

- フロントエンド
- バックエンドAPI
- PostgreSQL
- Flutter Webビルド用コンテナまたはビルドワーカー

### 7.2 Flutter SDK

Flutter教材の実行にはFlutter SDKを利用する。

MVPでは、ブラウザ上でDart/Flutterを直接実行する方式ではなく、サーバー側でFlutter Webとしてビルドする方式を採用する。

理由は次の通りである。

- 実務に近いFlutterプロジェクト構成を扱える
- `lib/main.dart`以外の複数ファイル、依存関係、アセット、設定ファイルを扱える
- 将来的にテスト、状態管理、ルーティング、API連携の教材へ拡張しやすい
- テンプレート差し替え方式よりも実際の開発体験に近い

ビルド環境の隔離方針は [セキュリティ方針](02_セキュリティ方針.md) を参照する。

### 7.3 ビルド用ワークスペース

ビルド要求ごとに、教材の初期プロジェクトと学習者が編集したファイルをもとにビルド用ワークスペースを生成する。

MVP第一段階ではローカルDocker上の一時ディレクトリまたは一時コンテナを利用する。

MVP第二段階ではクラウド上の一時ワークスペースまたはコンテナへ移行する。

ビルド処理は、アプリケーション本体、DB、秘密情報、ホストファイルへアクセスできないように分離する。

## 8. LLM連携

LLM連携では、学習者向け質問、Admin向けロードマップ生成、教材生成、教材修正案生成を扱う。

MVPでは、特定のプロバイダーに強く依存しすぎないよう、バックエンド側にLLMクライアント層を設ける。

LLMへ渡す主なコンテキストは次の通りである。

- 教材本文
- 学習目標
- 現在のコード
- ビルドログ
- エラーログ
- ユーザーの質問

LLM生成物は自動公開せず、必ず`draft`として保存する。

LLMへ秘密情報、APIキー、DB接続情報、ホストパスを送らない。詳細は [セキュリティ方針](02_セキュリティ方針.md) を参照する。

## 9. コード保存とファイル入出力

MVPでは、学習者の編集コードはブラウザ上に保存する。

候補は次の通りである。

- IndexedDB
- LocalStorage

複数ファイルのプロジェクト全体を扱うため、主な保存先はIndexedDBを想定する。LocalStorageは、選択中教材ID、最後に開いたファイル、UI状態などの軽量な状態に限定する。

プロジェクト全体のダウンロードとアップロードにはZIP形式を利用する。

アップロード時には、危険なパス、巨大ファイル、ファイル数上限、Flutterプロジェクトとしての最低限の構成を検証する。

## 10. テストと品質管理

### 10.1 ESLint / Prettier

TypeScriptコードの静的解析とフォーマットにはESLintとPrettierを利用する。

MVPでは、厳格すぎるルールで実装速度を落としすぎない。ただし、未使用変数、型エラー、基本的なフォーマット崩れはCIまたはローカルチェックで検出できるようにする。

### 10.2 Vitest

ユニットテストにはVitestを採用する。

主な対象は次の通りである。

- API入力バリデーション
- 教材データ変換
- ファイルパス検証
- ビルド状態遷移
- LLM入出力整形

### 10.3 Playwright

主要画面のE2EテストにはPlaywrightを採用する。

MVPで優先するテスト対象は次の通りである。

- 教材一覧から教材詳細へ遷移できる
- ファイルツリーからファイルを選んで編集できる
- ビルド要求を送信し、ビルド状態とログを確認できる
- Admin画面で教材を作成または編集できる

## 11. 採用を見送る技術

### 11.1 ブラウザ内だけでのFlutter実行

ブラウザ内だけでFlutterコードを実行する方式は、MVPでは採用しない。

理由は次の通りである。

- 実務に近い複数ファイル構成を扱いにくい
- 依存関係、アセット、設定ファイル、ビルド設定を扱う範囲が限定される
- 今回の目的であるサーバービルド方式の検証にならない

### 11.2 テンプレート文字列差し替え方式

教材テンプレート内の一部だけを文字列差し替えする方式は採用しない。

理由は次の通りである。

- 編集対象が狭くなり、実務的なFlutter開発体験から離れる
- Widget分割、状態管理、ルーティング、API連携などを扱いにくい
- 将来的な多言語対応や本格的な課題設計に発展しにくい

### 11.3 Firebase中心の構成

Firebase中心の構成は、MVP第一段階では採用しない。

理由は次の通りである。

- ローカルDockerでアプリケーション全体を完結させる方針とずれる
- サーバー側Flutter Webビルド環境の分離が別途必要になる
- DB、認証、ストレージを早期にクラウドサービスへ寄せると、MVPの検証対象が広がりすぎる

ただし、将来的な認証、ホスティング、ストレージ候補として再検討する余地はある。

## 12. 将来検討する技術

第二段階以降で検討する技術は次の通りである。

| 領域 | 候補 | 検討タイミング |
| --- | --- | --- |
| 認証 | Auth.js / Firebase Authentication / Auth0 | 外部公開時 |
| 認可 | RBAC / Admin role | 外部公開時 |
| ビルドキュー | BullMQ / Cloud Tasks / SQS | 複数ビルド要求を扱う段階 |
| キャッシュ | Redis | ビルドキュー、レート制限、セッション管理が必要な段階 |
| 成果物ストレージ | S3 / Cloud Storage | クラウドサーバービルド方式 |
| ビルドワーカー | Cloud Run Jobs / ECS Tasks / Kubernetes Jobs | クラウド上でビルドを分離する段階 |
| 監視 | OpenTelemetry / Cloud Logging / Datadog | 外部公開時 |
| コード保存 | GitHub連携 | 学習履歴や提出機能が必要な段階 |
| 教材バージョン管理 | Gitベース管理 / DB履歴管理 | 教材レビュー運用を強化する段階 |

## 13. 技術選定の判断基準

本プロダクトでは、技術選定を次の基準で判断する。

- MVPの学習体験を短期間で検証できる
- サーバービルド方式を安全に実装できる
- ローカルDockerで再現しやすい
- 将来のクラウド化を妨げない
- Flutter以外の言語やフレームワークへ拡張しやすい
- 小規模チームで保守できる
- LLM連携と教材管理を過度に複雑化しない

初期段階では、技術的に最も重要な検証対象をFlutter Webビルド、ビルド環境の隔離、学習画面の統合体験に絞る。
