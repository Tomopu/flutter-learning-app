## AI Summary

変更は原則 PR 経由。コミットは目的単位で分割し Conventional Commits 形式（docs/feat/fix/refactor/test/chore）で記述。秘密情報のコミット禁止。仕様・設計変更はドキュメント更新を伴う。CIが失敗しているPRはマージしない。

## 1. 目的

Issue・ブランチ・コミット・Pull Request・レビュー・マージ・リリース・機密情報の扱いに関する基準を定義する。変更の意図・判断理由・レビュー結果・リリース履歴を追跡できる状態に保つことが目的である。

## 2. 適用範囲

ドキュメント変更・実装変更・GitHub上の運用作業・AIエージェントによる変更作業すべてに適用する。

## 3. 基本方針

- 変更は原則としてPull Requestを通じて取り込む。
- 1つのPull Requestには1つの目的を持たせる。
- 変更理由が分かる粒度でIssue・PR本文・コミットメッセージを残す。
- CIが失敗しているPull Requestは原則としてマージしない。
- 仕様・設計・標準に関わる変更は、関連文書の更新有無を確認する。
- 秘密情報・個人情報・認証情報をGitHubにコミットしない。

## 4. リポジトリ設定

### 4.1 既定ブランチ

既定ブランチは `main` を基本とする。`main` は常に次を満たす状態に保つ。

- ビルドまたは主要な検証が通る
- 既知の重大な不具合がない
- 秘密情報が含まれていない
- READMEまたは主要ドキュメントから現在の構成を辿れる

### 4.2 ブランチ保護

外部公開または複数人開発を開始する段階で、`main` に次の保護を設定する: PR経由マージの必須化 / CI成功の必須化 / 直接pushの禁止 / レビュー承認の必須化 / force pushとbranch deletionの禁止

個人開発段階では厳格な保護を省略してよい。ただし、履歴が追えるコミット単位とPR単位を保つ。

## 5. Issue運用

### 5.1 Issueを作成する条件

次のいずれかに該当する場合はIssueを作成する。

- 要求・設計・実装方針に判断が必要な場合
- 複数コミットまたは複数PRに分かれる作業を管理する場合
- バグ・不具合・仕様漏れ・技術的負債を記録する場合
- 後続対応や未決定事項を追跡する場合

軽微な誤字修正や単一ファイルの明確な修正では、Issueを省略してよい。

### 5.2 Issueに書く内容

背景 / 現状の問題 / 期待する状態 / 対象範囲 / 完了条件 / 関連文書・関連PR・関連Issue

設計判断に関するIssueでは、決定事項だけでなく、見送った案と理由も簡潔に残す。

## 6. ブランチ運用

### 6.1 ブランチ種別

| 種別 | 命名例 | 用途 |
|------|--------|------|
| 機能追加 | `feature/build-preview` | 新機能・画面・APIの追加 |
| 修正 | `fix/build-timeout` | バグ修正・不具合対応 |
| ドキュメント | `docs/github-workflow` | 文書・README・図・画像の更新 |
| リファクタ | `refactor/backend-build-service` | 外部仕様を変えない構造改善 |
| 調査 | `research/build-runtime` | 検証・調査・試作 |
| 保守 | `chore/update-deps` | 依存更新・設定変更・雑務 |

### 6.2 ブランチ作成ルール

- `main` または既定ブランチから作業ブランチを作成する。
- ブランチ名は英小文字・数字・ハイフンを基本とする。日本語ブランチ名は使用しない。
- 長期間作業するブランチは、定期的に既定ブランチとの差分を確認する。

## 7. コミット運用

### 7.1 コミット単位

目的が異なる変更は別コミットにする。例: 仕様書の清書 / ディレクトリ移動 / 旧ファイル削除 / 実装変更 / テスト追加 / READMEの更新

### 7.2 コミットメッセージ

```text
<type>: <変更内容>
```

| type | 用途 |
|------|------|
| `docs` | ドキュメント・README・画像・図の変更 |
| `feat` | ユーザー向け機能追加 |
| `fix` | バグ修正 |
| `refactor` | 仕様を変えない構造改善 |
| `test` | テスト追加・修正 |
| `chore` | 設定・依存関係・開発補助 |
| `ci` | CI設定 |

例: `docs: GitHub運用基準を追加` / `feat: 教材一覧画面を追加` / `fix: ビルドタイムアウト時の状態更新を修正`

### 7.3 AI支援時のコミット

コミット単位とメッセージ規則は人間の作業と同じ基準を適用する。AI生成内容をそのまま採用する場合でも、PR作成者またはレビュー担当者は次を確認する。

- 既存仕様・設計書・標準文書との矛盾がないこと
- 不要なファイル・重複ファイル・一時ファイルが含まれていないこと
- 秘密情報やローカル環境依存の情報が含まれていないこと
- 参照リンク・相対パス・画像パスが壊れていないこと

## 8. Pull Request運用

### 8.1 PR作成条件

- 変更の目的が説明できる
- 主要な差分を自己確認している
- 実行可能な範囲でテストまたは確認を行っている
- 未完了の場合はDraft PRとして作成している

### 8.2 PR本文

PR本文には次の項目を書く。

```md
## 概要

## 変更内容

## 確認内容

## 影響範囲

## 関連Issue / 関連文書
```

ドキュメントのみのPRでは確認内容に「リンク・目次・相対パスを確認した」などを書く。実装PRでは実行したテスト・動作確認手順・未確認事項を書く。

### 8.3 PRサイズ

- 仕様変更と実装変更が大きい場合は、先に仕様・設計PRを作る。
- 画像移動・旧ファイル削除・README更新は、必要に応じて別コミットまたは別PRに分ける。
- レビューが困難な巨大PRは、機能単位・レイヤー単位・文書単位に分割する。

## 9. レビュー運用

### 9.1 レビュー観点

- 要求仕様・設計書・標準文書との整合性
- ユーザー影響・破壊的変更・移行作業の有無
- セキュリティ・秘密情報・権限境界への影響
- テスト・動作確認・未確認事項の妥当性
- ドキュメント・README・トレーサビリティの更新漏れ
- 不要なファイル・生成物・一時ファイルの混入

### 9.2 レビューコメント

- 修正必須の指摘は理由と期待する修正方針を書く。
- 任意提案は必須指摘と区別する。
- 設計判断が必要な指摘は、必要に応じてIssueまたは設計書に残す。
- 解決済みのコメントは修正内容を確認してからResolveする。

## 10. CI / GitHub Actions

- CIはPull Request単位で実行する。
- 実装PRでは lint・type check・test・build のうち該当するものを実行する。
- ドキュメントPRでは必要に応じてリンクチェック・Markdown lint・画像パス確認を行う。
- CI失敗を無視してマージする場合はPR本文またはコメントに理由を残す。

## 11. マージ運用

### 11.1 マージ条件

- レビュー指摘が解決している
- 必要なCIが成功している
- PR本文に確認内容が書かれている
- 関連文書の更新漏れがない
- 秘密情報や不要ファイルが含まれていない

### 11.2 マージ方式

- 小さな修正や単一目的のPRはSquash mergeを優先する。
- 意味のある複数コミットを残したいPRはMerge commitを検討する。
- Rebase mergeは、履歴管理方針が明確な場合に限る。

## 12. リリースとタグ

リリースを作成する場合は、リリース対象の範囲・主な変更内容・破壊的変更・移行手順・既知の問題を残す。バージョン番号を運用する場合はSemantic Versioningの考え方を参考にする。

## 13. 機密情報とセキュリティ

- APIキー・アクセストークン・秘密鍵・DB接続情報・個人情報をコミットしない。
- `.env` などのローカル設定ファイルは `.env.example` のみを管理対象にする。
- 秘密情報を誤ってコミットした場合は、漏洩した値の失効・履歴対応・影響調査を行う。
- GitHub ActionsのSecretsは必要最小限の権限で設定する。
- 外部コントリビューターのPRでは、Actionsの権限とSecretsの露出に注意する。

## 14. ドキュメント同期

| 変更 | 確認する文書 |
|------|--------------|
| 要求変更 | 要求仕様書・ユースケース・受け入れ基準・トレーサビリティ |
| 画面変更 | 画面一覧・画面設計・UI方針・画像 |
| API変更 | API設計・バックエンド設計・トレーサビリティ |
| DB変更 | DB設計・バックエンド設計・API設計 |
| ビルド環境変更 | 実行環境アーキテクチャ・ビルド実行環境設計・セキュリティ方針 |
| LLM連携変更 | LLM連携設計・セキュリティ方針・要求仕様書 |
| GitHub運用変更 | 本文書・ドキュメント管理規定・README |

## 15. 禁止事項

- 秘密情報を含むファイルをコミットすること
- 意図不明な大量差分を1コミットにまとめること
- レビュー未完了またはCI失敗を理由なくマージすること
- 仕様変更をドキュメント更新なしで実装だけに反映すること
- 生成物・キャッシュ・一時ファイル・ローカル環境依存ファイルを混入させること
