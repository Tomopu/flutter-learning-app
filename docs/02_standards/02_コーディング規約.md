## AI Summary

TypeScript/Next.js/Node.js での実装規約。`any` 禁止、外部入力は境界で検証、秘密情報をフロントエンド・LLM・ログに渡さない。レイヤー分割（ルーティング/ユースケース/永続化）を守る。仕様・設計変更はドキュメント更新を必ず伴う。

## 1. 目的

実装時のコード品質・命名・責務分割・エラー処理・テスト・セキュリティに関する規約を定義する。MVPの実装速度を保ちながら、後から仕様変更やクラウド化を行える一貫性を確保する。

## 2. 基本方針

- 既存の設計・命名・ディレクトリ構成に合わせる。
- 型で表現できる制約は型で表現する。
- 外部入力は境界で検証する。
- エラーはユーザーと開発者が原因を追える形で扱う。
- 不要な抽象化を避け、実際に重複や複雑さを減らす場合にだけ共通化する。
- 実装中に仕様の不足や矛盾を見つけた場合は、該当ドキュメントを更新する。

## 3. TypeScript

### 3.1 型の扱い

- `any` の利用は避ける。`unknown` を使う場合は利用前に型を絞り込む。
- APIの入力と出力はスキーマまたは明示的な型で定義する。
- ドメイン上の状態は文字列リテラル型・ユニオン型・列挙的な型で表現する。
- `null`（DB由来の未設定値）と `undefined`（未指定の引数・オプション）を使い分ける。

### 3.2 命名

- 変数・関数・ファイル名は役割が分かる名前にする。略語は一般的なものに限定する。
- 真偽値は `is`・`has`・`can`・`should` などから始める。

### 3.3 依存関係

- 共有型やユーティリティは必要になってから抽出する。
- フロントエンドからバックエンド内部実装へ依存しない。
- ドメインロジックをUIコンポーネントやルーティング層に閉じ込めない。

## 4. フロントエンド

### 4.1 責務分割

- UI状態・サーバー状態・フォーム状態を混同しない。
- コンポーネントは表示責務が分かる単位で分割する。
- 画面固有の処理と再利用可能な部品を混在させない。

### 4.2 UI状態

画面では少なくとも次の状態を明示的に扱う: 読み込み中 / 成功 / 失敗 / 空状態 / 処理中

学習画面では、コード編集・ビルド状態・ログ表示・プレビュー・LLMチャット状態を混同しない。

### 4.3 アクセシビリティ

- ボタン・入力欄・リンクには役割が分かるラベルを付ける。
- キーボード操作を阻害しない。
- エラー・警告・成功は視覚表現だけに依存しない。

詳細は [UI方針](../03_design/02_ui/03_UI方針.md) を参照する。

## 5. バックエンド

### 5.1 レイヤー分割

次の責務を混在させない: ルーティング / 入力バリデーション / ユースケース / ドメインルール / 永続化 / 外部サービス連携

APIハンドラにビルド制御・DB操作・LLM呼び出し・レスポンス整形を過度に集中させない。

### 5.2 API境界

- 外部入力はAPI境界で検証する。ファイルパス・ファイルサイズ・ファイル数・ビルド設定は必ず検証する。
- Admin APIと学習者向けAPIは、ルーティング上も権限境界上も分けて扱う。

詳細は [API設計](../03_design/03_api/01_API設計.md) を参照する。

### 5.3 失敗しやすい処理

ビルド実行・ファイル入出力・LLM連携・外部API呼び出しは失敗する前提で実装する。

- 開始・成功・失敗・タイムアウトを記録する。
- ユーザーに返すエラーと内部ログを分ける。
- 秘密情報・ホストパス・内部実装の詳細をユーザー向けエラーに含めない。

## 6. データベース

- DBスキーマは設計書と矛盾しないようにする。
- マイグレーションは意図が分かる単位で作成する。
- 削除・公開状態変更・一括更新などの破壊的操作は、ユースケース側で意図を明確にする。
- JSON型を使う場合は、保存する構造と利用箇所を設計書に残す。

## 7. セキュリティ

- 学習者が編集したコード・アップロードファイル・LLM生成物は信頼しない。
- 秘密情報・APIキー・DB接続情報・ホストパスをフロントエンド・ビルド環境・LLMへ渡さない。
- ビルド環境はアプリ本体・DB・秘密情報から分離する。

詳細は [セキュリティ方針](03_セキュリティ方針.md) を参照する。

## 8. テスト

### 8.1 優先するテスト対象

ドメインロジック / API入力バリデーション / ファイルパス検証 / ビルド状態遷移 / LLM入出力整形 / 学習者とAdminの主要フロー

### 8.2 テストの粒度

- 純粋なロジックは単体テストで確認する。
- APIは正常系と主要な異常系を確認する。
- 学習者画面とAdmin画面の主要導線はE2Eテスト対象にする。
- バグ修正時は再発防止テストを追加する。

## 9. コメントとドキュメント

- コードから明らかな処理をコメントで説明しない。
- 複雑な制約・セキュリティ上の理由・設計上の判断は短くコメントする。
- 仕様や設計が変わった場合は、コードコメントだけで済ませず関連ドキュメントを更新する。

## 10. 禁止事項

- 意図不明な `any` の利用
- API境界で未検証の入力を内部処理へ渡すこと
- UIコンポーネントにバックエンド内部ルールを直接埋め込むこと
- 秘密情報をログ・レスポンス・ビルド成果物・LLMコンテキストに含めること
- 仕様変更をドキュメント更新なしで実装だけに反映すること
