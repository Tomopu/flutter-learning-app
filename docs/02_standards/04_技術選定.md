## AI Summary

Next.js + TypeScript + Hono + PostgreSQL(Prisma) + Monaco Editor + Docker + Flutter SDK。LLM はバックエンドのクライアント層経由。コード保存は IndexedDB。テストは Vitest + Playwright。第一段階はローカルDocker、第二段階でクラウドへ移行する想定で技術を選定している。

## 1. 目的

MVPで採用する技術スタックと選定理由を定義する。個別設計書で技術スタックに触れる場合は、本ドキュメントを参照する。

技術選定は、第一段階（ローカルDockerアプリ）を素早く実装できること、第二段階（クラウドサーバービルド）へ拡張できること、将来的な多言語対応を妨げないことを重視する。

## 2. 前提

### 2.1 第一段階: ローカルDockerアプリケーション方式

フロントエンド・バックエンド・DB・ビルド実行環境をローカルDocker上で動作させる。教材閲覧・コード編集・ビルド・プレビュー・LLM質問・教材管理の一連の体験をローカルで安定して動かすことを優先する。

### 2.2 第二段階: クラウドサーバービルド方式

GCP・AWSなどのクラウドにデプロイし、ビルド要求ごとに一時コンテナを生成する。認証・認可・ビルドキュー・リソース制限・成果物ストレージ・監視・コスト管理を追加で検討する。

## 4. フロントエンド

### 4.1 Next.js

教材一覧・学習画面・Admin画面をページ単位で整理でき、将来的にAPI境界や認証を追加しやすい。UIはReactコンポーネントとして実装する。

### 4.2 TypeScript

フロントエンドとバックエンドの両方にTypeScriptを使い、API境界での型不整合を減らす。

### 4.3 CSS Modules / 純CSS

色・余白・文字サイズ・ボタン・パネルなどの基本スタイルはCSS変数と共通クラスで管理する。コンポーネント固有のスタイルはCSS Modules、グローバルなリセット・テーマ・タイポグラフィはグローバルCSSで管理する。Tailwind CSSは採用しない。

### 4.4 Monaco Editor

複数ファイル編集・Dart/JSON/YAML/Markdownのシンタックスハイライト・将来的な補完や診断表示への拡張を考慮して選定した。

## 5. バックエンド

### 5.1 Node.js

フロントエンドと同じTypeScriptで実装でき、API型・バリデーション・ドメイン型を共有しやすい。ビルド制御・ファイル操作・LLM API連携の実装に適している。

### 5.2 Hono

軽量で責務分離を表現しやすく、将来的な実行環境変更にも対応しやすい。APIは学習者向け・管理者向け・ビルド実行・LLM連携で責務を分ける。詳細は [API設計](../03_design/03_api/01_API設計.md) を参照する。

### 5.3 FastAPIを採用しない理由

フロントエンドとバックエンドをTypeScript中心で揃えて実装速度と型共有を優先するため、主軸にしない。将来Python製の教材解析・LLM評価・バッチ処理が必要になった場合は、バックエンドと分離した補助サービスとして追加する。

## 6. データベース

### 6.1 PostgreSQL

教材・ロードマップ・ビルド履歴・LLM生成履歴をリレーショナルに管理でき、JSON型でLLM入出力や柔軟なメタデータも保存できる。詳細は [DB設計](../03_design/04_data/01_DB設計.md) を参照する。

### 6.2 Prisma

TypeScriptから型安全にDBアクセスでき、スキーマとマイグレーションを管理しやすい。

## 7. ビルド実行環境

### 7.1 Docker

フロントエンド・バックエンド・DB・ビルド環境を同じ手順で起動でき、Flutter SDKをアプリ本体から分離できる。将来のクラウドコンテナ実行へつなげやすい。

Docker Compose で起動するサービス: フロントエンド / バックエンドAPI / PostgreSQL / Flutter Webビルドコンテナ

### 7.2 Flutter SDK

実務に近いプロジェクト構成（複数ファイル・依存関係・アセット・設定ファイル）を扱えるため、サーバー側でFlutter Webとしてビルドする方式を採用する。ブラウザ内実行方式は採用しない。

ビルド環境の隔離方針は [セキュリティ方針](03_セキュリティ方針.md) を参照する。

### 7.3 ビルド用ワークスペース

ビルド要求ごとに、教材の初期プロジェクトと学習者の編集ファイルをもとにワークスペースを生成する。アプリ本体・DB・秘密情報・ホストファイルへアクセスできないよう分離する。

## 8. LLM連携

学習者向け質問・Admin向けロードマップ生成・教材生成・修正案生成を扱う。特定プロバイダーへの依存を避けるため、バックエンド側にLLMクライアント層を設ける。

LLM生成物は必ず `draft` として保存する。秘密情報・APIキー・DB接続情報・ホストパスは渡さない。詳細は [セキュリティ方針](03_セキュリティ方針.md) を参照する。

## 9. コード保存とファイル入出力

学習者の編集コードはブラウザ上に保存する。主な保存先はIndexedDB（複数ファイルのプロジェクト全体）。LocalStorageは選択中教材ID・UI状態などの軽量な状態に限定する。

プロジェクト全体のダウンロード・アップロードにはZIP形式を使用する。アップロード時は危険なパス・巨大ファイル・ファイル数上限・Flutterプロジェクト構成を検証する。

## 10. テストと品質管理

- **ESLint / Prettier**: 未使用変数・型エラー・フォーマット崩れをCIまたはローカルチェックで検出する。
- **Vitest**: API入力バリデーション・教材データ変換・ファイルパス検証・ビルド状態遷移・LLM入出力整形をユニットテストで確認する。
- **Playwright**: 教材一覧→詳細遷移・ファイル選択・ビルド実行・Admin教材作成の主要フローをE2Eテストで確認する。

## 11. 採用を見送る技術

| 技術 | 見送り理由 |
|------|------------|
| ブラウザ内Flutter実行 | 複数ファイル構成・依存関係・アセットを扱いにくい。サーバービルド方式の検証にならない |
| テンプレート文字列差し替え | 編集範囲が狭くなり実務的なFlutter体験から離れる。多言語対応・課題設計への発展が難しい |
| Firebase中心の構成 | ローカルDockerで完結させる方針と合わない。MVPの検証対象が広がりすぎる |

## 12. 将来検討する技術

| 領域 | 候補 | 検討タイミング |
|------|------|----------------|
| 認証 | Auth.js / Firebase Authentication / Auth0 | 外部公開時 |
| 認可 | RBAC / Admin role | 外部公開時 |
| ビルドキュー | BullMQ / Cloud Tasks / SQS | 複数ビルド要求を扱う段階 |
| キャッシュ | Redis | ビルドキュー・レート制限・セッション管理が必要な段階 |
| 成果物ストレージ | S3 / Cloud Storage | クラウドサーバービルド方式 |
| ビルドワーカー | Cloud Run Jobs / ECS Tasks / Kubernetes Jobs | クラウド上でビルドを分離する段階 |
| 監視 | OpenTelemetry / Cloud Logging / Datadog | 外部公開時 |
| コード保存 | GitHub連携 | 学習履歴や提出機能が必要な段階 |
| 教材バージョン管理 | Gitベース管理 / DB履歴管理 | 教材レビュー運用を強化する段階 |

## 13. 技術選定の判断基準

- MVPの学習体験を短期間で検証できる
- サーバービルド方式を安全に実装できる
- ローカルDockerで再現しやすい
- 将来のクラウド化を妨げない
- Flutter以外の言語・フレームワークへ拡張しやすい
- 小規模チームで保守できる
