## AI Summary

docs/ 配下の文書管理規定。正式文書にはメタ情報と AI Summary を付ける。正本は1か所に書き他から参照リンクで済ませる。要求ID は FR/NFR/UC/AC/DR/OPEN プレフィックス。下書きは 99_drafts/ に置く。文書はAIと人間のコストを意識して簡潔に書く。

## 1. 目的

このドキュメントでは、`docs/` 配下の文書分類、更新方針、下書きの扱い、文書メタ情報、要求仕様書の書き方を定義する。

この規定は、正式文書を実装判断の根拠として使える状態に保つための基準である。

## 2. 基本方針

- 正式文書と下書きを分けて管理する。
- 正式文書は実装判断の根拠として扱う。
- 下書きは未整理の検討、長文メモ、試作、調査途中の情報を置く場所として扱う。
- 実装時に参照する内容は、下書きではなく正式文書へ反映してから使う。
- 同じ情報を複数文書に重複して書かない。正本を1つ決め、他文書から参照する。

## 3. ディレクトリ分類

- `01_requirements/`: 何を作るか、何を満たすか。
- `02_standards/`: どのような規約や方針で作るか。
- `03_design/`: 要求をどう実現するか。
- `04_project/`: いつ、どの順序で進めるか。
- `05_references/`: 外部情報や参考リンク。
- `99_drafts/`: 下書き、未整理メモ、試作物。

画面イメージなど、特定の設計領域に属する画像は該当する設計ディレクトリの配下に置く。UI設計で参照する正式画像は、原則として `03_design/02_ui/00_images/` に置く。

## 4. 命名規則

- フォルダ名は英語を基本とする。
- Markdownファイル名は `01_要求仕様書.md` のように番号と日本語名を組み合わせる。
- 画像ファイル名は画面番号や用途が分かる名前にする。
- 可能であれば、画像名では括弧より `_` を優先する。
- 正式文書には、必要に応じて文書IDまたは要求IDを付ける。

## 5. 文書メタ情報

正式文書の冒頭には、原則として次の表を置く。

```md
| 項目 | 内容 |
|------|------|
| 文書ID | XXX-YYY-001 |
| 作成日 | YYYY-MM-DD |
| 更新日 | YYYY-MM-DD |
| 状態 | 草案 / レビュー中 / 正式 / 廃止 |
| 関連文書 | ... |
```

小さなREADMEや一時的な下書きでは省略してよい。ただし、要求仕様、標準、設計書の正本には付与する。

## 6. 要求仕様書の書き方

要求仕様書は、IEEE 830やISO/IEC/IEEE 29148の考え方を参考に、次の構成を基本とする。

- はじめに: 目的、範囲、用語、参照文書、文書構成
- 全体説明: プロダクトの位置づけ、ユーザー、制約、前提
- 外部インターフェース要求: UI、API、データ、外部サービス
- 機能要求: 要求ID、説明、優先度、受け入れ基準
- 非機能要求: セキュリティ、信頼性、性能、保守性、運用など
- 対象外、将来拡張、未決定事項
- トレーサビリティ: 要求、ユースケース、受け入れ基準、設計書の対応

要求文は、可能な限り「システムは...できること」「システムは...しなければならない」の形で書く。

## 7. 要求IDと分類

要求には、次のようなIDを付与する。

- `FR-XXX`: 機能要求
- `NFR-XXX`: 非機能要求
- `UC-XXX`: ユースケース
- `AC-XXX`: 受け入れ基準
- `DR-XXX`: 設計上の決定
- `OPEN-XXX`: 未決定事項

IDは一度発行したら、意味を大きく変えない。廃止する場合は削除ではなく、状態を「廃止」として残すことを優先する。

## 8. AI向け要約

AIに読ませるためだけの全文複製は避ける。

AI向けに短い情報が必要な場合は、正式文書の先頭に `AI Summary` を追加するか、将来的に `ai-context/` を作成して読む順番と短い要約だけを管理する。

`AI Summary` には、実装判断に必要な要点だけを書く。背景説明、検討ログ、長い比較表は含めない。`AI Summary` はメタ情報の直後に配置し、3文以内を目安とする。

## 9. 更新ルール

- 要求が変わった場合は、関連する設計書、受け入れ基準、トレーサビリティを確認する。
- 設計が変わった場合は、要求仕様との矛盾がないか確認する。
- 受け入れ基準が変わった場合は、要求IDとの対応を確認する。
- 下書きから正式文書へ反映した場合、必要に応じて下書き側に反映済みであることを残す。
- 正式文書を更新した場合は、冒頭の `更新日` を更新する。
- GitHub上で変更する場合は、[GitHub運用基準](05_GitHub運用基準.md) に従って、変更目的が追跡できるコミットまたはPull Requestにする。

## 10. 図の扱い

- 図は、可能な限りMermaidで管理する。
- UI設計で参照する画面イメージやスクリーンショットは `03_design/02_ui/00_images/` に置く。
- 下書き画像や旧画像は `99_drafts/05_images/` に置く。
- 図が設計判断の根拠になる場合は、関連する設計書から参照する。

## 11. 下書きの扱い

- 下書きは長くてもよい。
- 下書きは読みやすさよりも情報を失わないことを優先してよい。
- ただし、AIに読ませる文脈や実装判断では、下書き全文ではなく正式文書を優先する。
- 下書きの内容を採用したら、正式文書に整理して反映する。

## 12. 文書の品質と簡潔さ

- 文書はAIエージェントのコンテキストと人間の読解コストを意識して書く。
- 1つの事実は1か所に書く。繰り返しが必要な場合は参照リンクを使う。
- 自明な説明・「次の通りである」「以下に示す」のような冗長な前置き・体裁合わせの水増しは避ける。
- 採用理由は「その選択が自明でない理由」だけを書く。技術の一般的な利点を並べるだけでは理由にならない。
- 短くても情報が揃っていれば十分。長さは品質の代替ではない。
